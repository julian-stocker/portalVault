## Ablauf (ADR-0137)

1. **Arbeitsbaum sauber, Tests grün:** `npm test`, `npm run check`, `npm run verify:sums`.
2. **Preflight und Baselines:** `npm run db:migrate:staging -- 0169`
   Erwartet: Zeile 9999 = `0`. Zeile 9998 ist für den Prüfzugang > 0 — die Verkaufsbuch-Zeilen
   (121, 131–137) liest er bewusst nicht. **Zeile 121 als `postgres` im SQL-Editor nachsehen:**
   sie muss `0` sein, sonst stoppt `0171`.
3. **Einfügen:** `supabase/operations/staging-0169-0170-0171-0172-0173-0174.sql` vollständig in den SQL-Editor des
   Staging-Projekts, ausführen. Erwartet: die NOTICE-Zeilen `A3` und `0169-0174 ok`, dann
   `commit`. Bricht etwas ab, ist **nichts** angewendet (eine Transaktion).
4. **Nachkontrolle:** `npm run db:migrate:staging -- 0169 --resume`
   Erwartet: Zeile 9999 = `0`.
5. **Berechtigter Lauf als `postgres`:** `supabase/checks/0169-0170-0171-0172-0173-0174_postflight.sql` im SQL-Editor mit den
   eingefrorenen Baselines (der Runner legt die Datei mit eingesetzten Werten ab). Erwartet:
   **9998 = 0 und 9999 = 0**; 231–237 zeigen dieselben Werte wie Preflight 131–137.
6. **Rechte:** `npm run db:privileges:staging` (ADR-0140) — der Prüfzugang hat weiterhin genau
   zwölf Tabellen und drei Funktionen.
7. **Akte:** Zeilen in `supabase/migrations/APPLIED.md` von „lokal vorbereitet“ in die
   Staging-Tabelle verschieben (Datum, Prüfsummen, Protokolle), `npm run sums:write`.

  die zwei Sitzungen (eine verworfen, eine geschlossen) bleiben als Nachweis stehen.
